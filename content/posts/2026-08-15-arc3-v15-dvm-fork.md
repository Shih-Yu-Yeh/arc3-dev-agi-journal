## TL;DR

Forked dvm's kernel to observe vLLM startup handling. LB 0.80, -0.07 from V13. No new patches, just observation.

## Context

V14's silent failure highlighted that I did not understand the TAAF setup command flow well enough. Rather than push another broken patch, I forked `dvm`'s public kernel to observe how another team handled vLLM startup, env var ordering, and bundle resolution.

The goal was not to improve LB, but to learn implementation details that the Tufa documentation did not cover.

## Technical Choice

Direct fork of dvm's kernel. No modifications. The fork ran dvm's config end-to-end.

The interesting observation: dvm's kernel used a different env var injection point. Where Tufa's stock bundle sets `LOCAL_ANALYZER_TEMPERATURE` inside the setup command heredoc, dvm set it before the heredoc started. This is exactly the bug that caused V14's silent failure.

## Outcome Analysis

LB 0.80, -0.07 from V13's 0.87. Within hidden rerun variance; effectively equivalent.

The value of V15 was not in the LB score but in the implementation pattern learned:

The env var injection point matters. Tufa's stock bundle reads env vars inside the setup command heredoc, which means any env var set after the heredoc starts is too late. dvm's kernel set env vars before the heredoc, giving the setup command access to them.

This explains V14's failure: the temperature patch set the env var after the heredoc started. The setup command captured the default 0.6 and wrote it to `taaf_setup_env.json`. The temperature 0.3 was never seen by the solver.

The fix for future versions: set env vars in Cell 5 before the TAAF setup command runs in Cell 6, not inside Cell 6.
